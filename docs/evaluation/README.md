# Оценка движка браузерной конвертации

Документ фиксирует результаты проверки, проведённой **до** каких-либо изменений
в поставке. Ничего из описанного в репозиторий не интегрировано: это материал
для решения, а не описание работающей системы.

По итогам решения браузерный путь переведён на BetterOffice, а путь LOWA
удалён; текущее устройство — в `../local-engine.md`.

## Зачем проверяли

Браузерный маршрут держится на сборке LibreOffice в WebAssembly (ZetaOffice/LOWA):
328 МБ файлов в образе, около 78 МБ загрузки на первого посетителя, 1 ГБ линейной
памяти вкладки, обязательные заголовки COOP/COEP и открытый вопрос о праве на
раздачу бинарников (`../local-wasm.md`). Проверялось, можно ли заменить движок
на такой, который считает документы сам, — и какой ценой.

## Кандидаты

| Кандидат | Лицензия | Форматы | PDF | Вес |
|---|---|---|---|---|
| LibreOffice WASM (действующий) | неясна | XLSX, DOCX | пишет | 78 МБ загрузки, 328 МБ в образе |
| CasualOffice/core | Apache-2.0 | DOCX, ODT, MD, TXT — **без XLSX** | пишет (свой layout) | ~3.3 МБ заявлено |
| BetterOffice | Apache-2.0 | DOCX, XLSX, PPTX | **не пишет** | 3.85 МБ wasm + шрифты |
| OnlyOffice x2t (WASM) | **AGPL-3.0** | DOCX, XLSX, PPTX, PDF и др. | **не пишет** (см. ниже) | 9.2 МБ сжатый, 62.6 МБ распакованный |

### OnlyOffice: проверялся отдельно

Проверялись две сборки: `x2t.wasm` 9.4.0 из проекта `onlyoffice-web-comp` и
релизная сборка CryptPad (`cryptpad/onlyoffice-x2t-wasm`, тег `v9.3.0+0`:
35.9 МБ wasm, контрольная сумма sha512 сверена). Результат одинаковый.

| Задача | Код возврата |
|---|---|
| DOCX → ODT | **0** (успех, 171 мс) |
| DOCX → `Editor.bin` (`CANVAS_WORD`) | **0** (успех; обратная конвертация в DOCX отдаёт исходный текст) |
| `Editor.bin` → PDF | **80** (ошибка) |
| DOCX → PDF (явные форматы) | **80** (ошибка) |
| `<пустой pdf.bin>` → PDF | 0 — пустой PDF (0 страниц) |
| `<чужой pdf.bin>` → PDF | 0 — PDF с **чужим** содержимым |

PDF в OnlyOffice делается в **три шага**, и x2t умеет только первый и третий:

1. документ → `Editor.bin` — умеет x2t (проверено);
2. `Editor.bin` → **PDF-метафайл** (файл `pdf.bin`) — делает редактор sdkjs;
3. `pdf.bin` → PDF-файл — умеет x2t (PdfWriter собран: в wasm есть
   `NSOnlineOfficeBinToPdf`, `PdfWriter`).

Последний опыт это и подтвердил: подложив чужой `pdf.bin` из их тестового
набора, получаем валидный PDF с содержимым **того** документа — в `pdf.bin`
лежат строки «Heading », «Heaing » их тестовой страницы. Свой документ через
этот путь не проходит: шаг 2 в WASM-сборке отсутствует — ровно то, о чём
предупреждает npm-пакет `@x2t/wasm`: «PDF, SVG and image output formats require
the OnlyOffice Canvas renderer, which is not included in the WASM build».

PDF в этом стеке делает не x2t, а редактор sdkjs: только его PDF-подсистема —
49 МБ (из них `drawingfile.wasm` 9.8 МБ), а весь sdkjs — 226 МБ, статика
web-apps — 695 МБ. Вес получился бы больше, чем у действующей сборки
LibreOffice, — то есть выигрыша, ради которого затевается замена, нет.

Юридически x2t распространяется под **AGPL-3.0** с дополнительными условиями
(Section 7): сетевой копилефт (пользователям, взаимодействующим с программой
по сети, нужно предоставить исходный код) и обязательное сохранение логотипа
ONLYOFFICE — убрать его можно только в платной Developer Edition. Для сервиса,
отдающего результат наружу, это ограничение существеннее технических.

CasualOffice отпал по трём причинам: таблиц нет вовсе (в Rust-workspace нет
крейтов для них), FilterData и `ScaleToPages` отсутствуют как понятие, а
опубликованный npm-пакет не содержит wasm-бинарника — `init()` падает. Собирать
его пришлось бы из исходников при каждом обновлении.

BetterOffice проверялся подробно: у него есть постраничный layout
(`compute_layout` → страницы с позиционированными фрагментами) и display list
(«renderer-agnostic paint primitives per page»), но **записи PDF в API нет** —
экспорт только обратно в OOXML, Markdown и PNG. Поэтому проверялась связка
«BetterOffice даёт layout и глифы, PDF собираем сами».

## Что измерено

Замеры сняты на двух документах: `ru.docx` (12 абзацев кириллицы, фикстура
проекта) и `sds.docx` (реальный документ на 16 страниц: китайский и латиница,
таблицы, логотип, пиктограммы).

| Метрика | LOWA (действующий) | BetterOffice + свой PDF |
|---|---|---|
| Вес загрузки | ~78 МБ (сжатый) | **7.3 МБ** несжатых (~3 МБ gzip) |
| Из них WASM | 154 МБ распакованных | 3.85 МБ — только модуль layout |
| COOP/COEP | обязательны | **не нужны** (конвейер прошёл без заголовков) |
| Главный поток | не блокируется (pthread) | не блокируется (Web Worker) |
| Время, 16 страниц | — | **364 мс** (LibreOffice нативно — 906 мс) |
| Размер PDF, 16 страниц | — | 216 КБ (LibreOffice — 462 КБ) |

Отдельно проверено, что `parse`, `opc` и `edit` модули движка при конвертации
не запрашиваются вовсе: для «прочитать, разложить, отдать примитивы» хватает
модуля layout.

## Главная находка: пагинация совпала с LibreOffice

Разбивка на страницы — то, ради чего движок и берётся: свой layout-движок должен
давать столько же страниц, сколько даёт серверный путь, иначе верстка расходится
не в деталях, а структурно.

| Движок | Страниц в `sds.docx` |
|---|---|
| LibreOffice (серверный эталон) | **16** |
| BetterOffice | **16** |
| CasualOffice | 30 |

Оба замера BetterOffice (в Node и в браузере) дали одинаковый результат, а на
эталонном документе совпали со страницами LibreOffice.

## Чего в проверке нет

Прототип экспортёра PDF писался как проверка гипотезы и **не доведён**:

1. **Текстовый слой сломан.** Иероглифы извлекаются из PDF как «标»: визуально
   символы на месте, но копирование, поиск и доступность не работают, а для
   PDF/A корректный `ToUnicode` обязателен. Причина — текст рисует библиотека
   своим шейпингом; лечится рисованием глифами движка (в display list есть
   глиф-индексы, координаты и advance) со своим `ToUnicode`.
2. **Изображения не выводятся** — в эталоне есть логотип и пиктограммы GHS,
   в прототипе их нет.
3. **Начертания не различаются** — заголовки в эталоне жирные, в прототипе
   часть ранов рисуется шрифтом по умолчанию.
4. **Параметры экспорта не начаты**: PDF/A (XMP, цветовой профиль), водяной
   знак, сжатие изображений, версия PDF. Движок их не предоставляет — всё это
   пришлось бы реализовывать поверх своего экспортёра.
5. **Пагинация книг отсутствует в API.** Для DOCX движок отдаёт готовые
   страницы, для XLSX — только `printDisplayList(sheet, range, metrics, gridlines)`,
   где «paper size and pagination are chosen by the caller». Разбивку листа на
   страницы, область печати и масштаб пришлось бы реализовывать самим.
6. **Память вкладки не измерена**: в воркере `performance.memory` недоступен,
   а `measureUserAgentSpecificMemory` требует изоляции, которая этому движку
   как раз не нужна.

## Образцы

`samples/` — один и тот же документ, сконвертированный тремя движками, и
первые страницы в PNG:

| Файл | Чем сделан |
|---|---|
| `docx-betteroffice.pdf` | BetterOffice + прототип своего экспортёра (16 стр.) |
| `docx-casualoffice.pdf` | CasualOffice, нативная сборка (30 стр.) |
| `docx-libreoffice.pdf` | серверный маршрут проекта, LibreOffice через UNO (16 стр.) |

Разницу видно по первой странице: в эталоне есть логотип, пиктограммы и жирные
заголовки; в `docx-betteroffice.pdf` их нет, а `docx-casualoffice.pdf`
разошёлся по числу страниц почти вдвое.

## Что это значит для проекта

- **Выигрыш по весу и требованиям реален**: 7 МБ против 78 МБ, изоляция не
  нужна, время конвертации меньше, чем у нативного LibreOffice при том же
  числе страниц.
- **Паритет с серверным путём перестаёт быть тождеством**, но и не теряется
  в разбивке: гейт из `../local-wasm.md` («те же параметры экспорта, та же
  подгонка под страницу») требует переформулировки — параметров экспорта
  у движка нет, а наивная замена движка на CasualOffice такой паритет
  нарушила бы сильнее: он давал 30 страниц там, где их 16, и вовсе не имеет XLSX.
- **Объём работ больше, чем «замена сборки»**: помимо интеграции движка нужен
  собственный экспортёр PDF (глифы, `ToUnicode`, изображения, декорации) и
  собственная пагинация книг. Текстовый слой и изображения — не мелочи:
  без них результат хуже нынешнего.
