# Архитектура

## Компоненты

| Компонент | Роль | Масштабируется |
|---|---|---|
| `api` (NestJS) | Приём файлов, оценка сложности, постановка задач, статусы | Горизонтально, без состояния |
| `uno-worker-*` | Конвертация: soffice + UNO-бридж + воркер BullMQ | Репликами, по длине очереди |
| `autoscaler` | Поднимает и гасит реплики в compose | Один экземпляр |
| `minio` | Входные файлы и результаты | Внешний S3 в проде |
| `valkey` | Очередь BullMQ, состояние задач | Один экземпляр (в проде — кластер) |
| `web` (nginx) | Интерфейс и реверс-прокси к api | Горизонтально |

Ключевое свойство: **api не конвертирует**. Он остаётся лёгким (десятки
мегабайт памяти), а вся тяжёлая работа идёт в отдельных контейнерах, которых
в простое может не быть вовсе.

## Поток задачи

```
POST /convert/to-pdf
  │
  ├─ multer: файл в память, лимит MAX_FILE_BYTES
  ├─ zod: параметры конвертации
  ├─ расширение и сигнатура (PK — контейнер OOXML)
  ├─ zip-гард: бомбы, traversal, дубликаты записей, макросы
  ├─ вид документа: xl/workbook.xml или word/document.xml
  ├─ оценка сложности: размер + листы книги или страницы документа
  ├─ MinIO: incoming/{jobId}.{ext}
  ├─ Redis: job:{jobId} → queued
  └─ BullMQ: задача в xlsx2pdf.{tier}
                    │
        ┌───────────┘
        ▼
  uno-worker (concurrency: 1)
  ├─ Redis: job:{jobId} → processing
  ├─ MinIO → /tmp/input.{ext}
  ├─ python3 uno_convert.py --format {xlsx|docx}
  │     └─ UNO → soffice (127.0.0.1:2002)
  │           ├─ loadComponentFromURL (Hidden, ReadOnly, без макросов)
  │           ├─ PageStyle: ScaleToPagesX/Y = 1 (только для книг)
  │           ├─ FilterData: водяной знак, качество, версия, шифрование
  │           └─ storeToURL (calc_pdf_Export | writer_pdf_Export)
  ├─ MinIO: results/{jobId}.pdf
  ├─ Redis: job:{jobId} → completed + ключ результата
  └─ /tmp очищается в finally
```

Вид документа определяется по содержимому zip-контейнера, а не по расширению:
сигнатура у книги и документа одна и та же, а расширению клиента верить
нельзя. Определение идёт после zip-гарда — разбирать оглавление контейнера,
не прошедшего проверку, незачем.

## Почему так

**Почему UNO, а не CLI.** `soffice --convert-to` не даёт ни доступа
к страничному стилю (а без него не выполнить «таблица на одной странице»),
ни полного набора FilterData (водяной знак, версия PDF, шифрование).
Вдобавок каждый вызов CLI поднимает новый процесс LibreOffice вместо
использования уже запущенного.

**Почему один маршрут на два формата.** Расширение из имени файла —
подсказка, а не доказательство: выбирать по нему фильтр экспорта значило бы
доверять клиенту там, где содержимое можно проверить. Файл без расширения
при этом остаётся конвертируемым — формат определяется по главной части
пакета (`xl/workbook.xml` против `word/document.xml`), а расширение служит
только для сверки с содержимым.

**Почему один soffice на воркер.** UNO не потокобезопасен: параллельные
вызовы в один бридж приводят к порче документа и падению процесса.
Параллелизм достигается только репликами.

**Почему три очереди.** Одна конвертация занимает воркер целиком. В общей
очереди крупный документ на несколько минут задерживал бы файлы, которые
проходят за секунды, — а стоят они одинаково с точки зрения клиента.

**Почему форматы не разведены по очередям.** Книгу и документ конвертирует
один и тот же процесс soffice, различается только фильтр экспорта: отдельные
очереди под каждый формат означали бы вдвое больше простаивающих реплик
(у средней и тяжёлой очереди минимальное число реплик — 1) при том же
времени конвертации. От конкуренции защищает деление по сложности, а не
по формату.

**Почему MinIO, а не общий том.** Реплики масштабируются и могут оказаться
на разных узлах; «общий каталог» перестаёт быть общим. Через объектное
хранилище решается и отдача результата: presigned-ссылка уходит клиенту
напрямую, минуя API.

**Почему Python-процесс на задачу.** Модуль `uno` не рассчитан на несколько
независимых сессий в одном интерпретаторе, а падение скрипта не должно
уносить с собой бридж. Отдельный процесс на задачу стоит миллисекунды
на старте и даёт изоляцию.

**Почему состояние задачи в Redis, а не в BullMQ.** BullMQ удаляет
завершённые задачи (`removeOnComplete`), а статус должен отвечать клиенту
ещё сутки — в том числе ссылкой на результат. Поэтому запись `job:{jobId}`
живёт своей жизнью с TTL.

## Что осталось от прежней версии

Сервис вырос из конвертера на WASM-сборке LibreOffice с Р7-совместимым API.
Оттуда остались и переиспользуются: обработка ошибок и фильтр исключений,
логгер pino, ограничитель частоты, лимиты безопасности, zip-гард и проверка
сигнатур, healthcheck-скрипты.

Удалены безвозвратно: `@matbee/libreoffice-converter`, fork-пул
(`fork-pool.ts`, `fork-worker.ts`), слой `sandbox`, Р7-эндпоинты
(`ConvertService.ashx`, `/status`, `/results`), загрузка по URL, xml-гард,
идемпотентность по `key`, файловое хранилище и поддержка остальных форматов.
Возвращать их не следует: причины отказа — память (1.16 ГБ на процесс,
которая не освобождалась между задачами) и отсутствие доступа к страничному
стилю и FilterData.
