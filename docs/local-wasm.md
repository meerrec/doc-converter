# Браузерный путь: конвертация и предпросмотр в браузере

Документ описывает локальный (клиентский) путь конвертации: LibreOffice,
собранный в WebAssembly, работает в браузере пользователя, документ никуда
не отправляется. Серверный путь (API, очередь, UNO-воркер) при этом
не меняется и остаётся основным.

Путь **работает**: браузерный маршрут главной страницы поднимает сборку,
открывает документ в предпросмотре и отдаёт готовый PDF на скачивание.
Проверено прогоном в headless-браузере на той же сборке, что раздаётся:
книга Excel на два листа открылась, предпросмотр нарисовал её в canvas,
конвертация вернула PDF на две страницы, память за серию из десяти
конвертаций не изменилась ни на байт.

Устройство движка — в `packages/office/src/`: `boot.ts` поднимает сборку,
`preload.ts` качает её файлы с прогрессом, `session.ts` разговаривает
с воркером, `queue.ts` ведёт очередь офиса, `paths.ts` выдаёт пути исходников,
`bridge/` исполняется внутри офиса, `filterData.ts` собирает параметры
экспорта. Страница (`apps/web`) знает адреса файлов и рисует компоненты —
и только это: движок переносим, и за границей пакета следит
`tests/office-imports.test.js`. Ниже зафиксировано то, что проверено, —
чтобы эти же грабли не собирались повторно.

## Откуда берётся сборка LibreOffice

Своя WASM-сборка **не собирается**: сборка берётся готовой у вендора
(ZetaOffice, allotropia) и раздаётся со своего nginx — тем же способом, что
и остальная статика. Причина отказа от самостоятельной сборки: она требует
машины с десятками гигабайт памяти, часов на линковку и отдельного раннера,
то есть несоразмерна задаче.

Следствия, определившие схему:

- **Версию приходится пинить по содержимому.** У вендора доступен
  единственный путь `zetaoffice_latest` (версионированных сборок на CDN нет:
  `zetaoffice_24.2`, `zetaoffice_25.8` и другие отвечают 404). Поэтому файлы
  скачиваются один раз, их контрольные суммы записываются в
  `apps/web/lowa/assets.sha256`, и сборка образа сверяет скачанное с этим
  файлом. Обновление сборки — осознанное действие: `apps/web/lowa/fetch.mjs`,
  просмотр изменений, коммит.
- **Файлы скачиваются распакованными.** CDN отдаёт их с brotli-сжатием
  (`content-encoding: br`) и делает это независимо от заголовка
  `Accept-Encoding`: запрос с `identity` получает тот же `br`. Поэтому
  скачивание делает Node (`fetch` распаковывает brotli сам), а не curl:
  системный curl на macOS brotli не понимает вовсе. Ошибка здесь не видна
  по размеру — 36 МБ вместо 161 МБ выглядят как правдоподобный wasm, —
  и проявляется только в браузере отказом компиляции модуля. Поэтому скрипт
  проверяет сигнатуры (`\0asm` у wasm, `PK\x03\x04` у образа ФС) и падает,
  если файл не распакован.
- **Раздача своя, а не с чужого CDN.** Так путь работает в закрытых контурах,
  где внешний CDN недоступен. Адрес источника вынесен в переменную
  `LOWA_SOURCE_URL`, поэтому зеркало подставляется без правки кода.

> **Открытый вопрос: право на раздачу.** Условия распространения этих
> бинарников вендор не публикует — на сайте сказано «Both options are
> possible» (и CDN, и self-hosting) с отсылкой к контактам, а внутри сборки
> есть Qt5, у которой свои лицензионные условия. До ответа вендора файлы
> используются для проверки гипотезы, а не для поставки.

## Проверка возможностей сборки (гейт)

Браузерный путь имеет смысл только при полном паритете с серверным:
те же параметры экспорта, та же подгонка под страницу. Проверка шла
на той же самой сборке (`cdn.zetaoffice.net/zetaoffice_latest`), которая
и будет раздаваться, — то есть результат относится к ней напрямую.

| Что проверялось | Результат | Как проверялось |
|---|---|---|
| Модуль Calc | есть | `private:factory/scalc` создаёт документ |
| Модуль Writer | есть | `private:factory/swriter` создаёт документ |
| Открытие XLSX | работает | книга на два листа открылась, число листов совпало |
| Страничный стиль `ScaleToPages` | работает | свойства приняли оба стиля, исключений нет |
| Экспорт PDF из книги | работает | `storeToURL` с `calc_pdf_Export` даёт файл |
| `FilterData` (PDF/A, водяной знак, качество) | работает при явной типизации | см. ниже |
| Предпросмотр книги | работает | лист нарисован в canvas, число листов вернулось |
| Предпросмотр документа Word | работает | абзацы нарисованы, интерфейс офиса убран |
| Экспорт PDF из документа Word | работает | `writer_pdf_Export` даёт PDF на две страницы |
| Память за серию конвертаций | не растёт | десять конвертаций подряд: размер памяти не изменился |

### Главная находка: FilterData требует типизированной последовательности

Экспорт PDF принимает `FilterData` — последовательность
`com.sun.star.beans.PropertyValue`. Она лежит внутри `any`, и способ
её передачи решает, дойдут ли параметры до экспортёра:

- **обычный массив** (`[{Name: 'SelectPdfVersion', Value: 1}]`) — параметры
  **молча игнорируются**. Файл получается валидный, но без PDF/A,
  без водяного знака и без сжатия. Так ведёт себя обвязка zetajs:
  в её коде (`zeta.js`, `getAnyType`) любой JS-массив превращается
  в последовательность `any` — `[]any`, а экспортёр ожидает
  `[]com.sun.star.beans.PropertyValue` и чужой тип не разбирает;
- **типизированная последовательность** — параметры применяются.
  Измерено на одном и том же документе: обычный PDF 1281 байт,
  PDF/A 15 269 байт (в метаданных появляется `pdfaid`), PDF
  с водяным знаком и качеством 50 — 7106 байт.

Отсюда правило для своей обвязки: **тип последовательности
`[]com.sun.star.beans.PropertyValue` задаётся явно**, а не выводится
из JS-значения. Проверять это надо не по факту «файл создался»,
а по содержимому: наличие маркера `pdfaid` в PDF/A и отличие размера
от базового экспорта.

Проверка выполнялась страницей-спаем в headless-браузере: она создаёт
книгу, применяет стиль, экспортирует PDF четырьмя способами (без
`FilterData`, с нетипизированной, с типизированной, с водяным знаком)
и сверяет размеры и маркеры.

## Предпросмотр: что даёт canvas

Canvas в Qt-сборке — это **редактор целиком**, а не просмотрщик страниц:
на проверке в нём отрисовались меню, панели инструментов, строка формул,
боковая панель и строка состояния вокруг листа с данными. Данные
отрисовываются верно (кириллица без квадратов, оба листа на месте),
но «страницами документа» такой предпросмотр не является.

Убрать интерфейс удалось **частично**, и способы для разных частей разные:

| Что скрывается | Как | Результат |
|---|---|---|
| Панели инструментов | `LayoutManager.hideElement` по именам из `/org.openoffice.Office.UI.<Модуль>WindowState/UIElements/States` | работает |
| Меню, строка состояния | тот же `hideElement`, но имена в перечне окон **не значатся** — задаются явно (`private:resource/menubar/menubar`), и повторно **после** перехода в полноэкранный режим: он возвращает меню на место | работает |
| Строка формул | `.uno:InputLineVisible` с аргументом `InputLineVisible = false` | команда принимается, эффекта нет |
| Боковая панель | `controller.Sidebar.Visible` | свойство недоступно |
| Баннер «документ открыт только для чтения» | не открывать документ со свойством `ReadOnly` | работает |

Итого остаются строка формул и боковая панель. Похоже, управление
интерфейсом в этой сборке реализовано неполно: часть команд принимается
без ошибки, но не влияет на отрисовку. Полноценного «режима просмотра»
из коробки нет — либо принимаем офисный вид, либо показываем не виджет,
а изображения страниц, полученные экспортом.

### Чего делать не надо: настройки конфигурации ломают отрисовку

Тот же интерфейс можно убрать и через конфигурацию офиса — записать
`Visible = false` в `/org.openoffice.Office.UI.<Модуль>WindowState/UIElements/States`
и вызвать `commitChanges()`. Так делает сам LibreOffice, и на настольной
сборке это работает. **В браузерной — нет, и вреда больше, чем пользы:**
окно загружается, документ открыт, `getSheets()` возвращает верное число
листов, а canvas остаётся пустым серым прямоугольником. Ошибок при этом
не возникает ни одной.

Проверено сравнением: с настройкой конфигурации — пустой canvas, без неё —
документ на экране. Поэтому интерфейс убирается только у созданного окна
(`LayoutManager`), а конфигурация не трогается вовсе.

## Известные ограничения

- **Память.** Линейная память WASM — 1 ГБ (потолок wasm32 — 4 ГБ),
  и не уменьшается никогда: таково свойство модели. Проверено серией
  из десяти конвертаций подряд (открыть книгу → экспорт PDF → закрыть):
  размер памяти не изменился ни на байт — ни общего роста, ни прироста
  на последней итерации, то есть рецикл страницы по этой проверке
  не требуется. Оговорка: метрика грубая — линейная память растёт
  ступенчато, и утечка меньше шага роста в неё не видна. Окончательный
  ответ дал бы прогон на крупных книгах и с большим числом итераций.
- **Недетерминированный размер результата.** PDF с метаданными (например,
  PDF/A) от прогона к прогону отличается на байты: измерено 15 269
  и 15 270 байт для одного и того же документа. Проверять применение
  параметров экспорта надо по признакам в содержимом (маркер `pdfaid`,
  отличие от базового экспорта), а не по совпадению размеров.
- **Размер загрузки.** Распакованные файлы: `soffice.wasm` 154,2 МБ,
  `soffice.data` 94,9 МБ, `soffice.js` 858 КБ, метаданные образа ФС 215 КБ.
  По сети они идут сжатыми gzip-копиями (51,0 и 26,9 МБ) — около 78 МБ
  на первого посетителя, дальше кэш браузера. На диске образа сборка занимает
  около 250 МБ: сжатые копии лежат рядом с распакованными, потому что nginx
  отдаёт их через `gzip_static`, не тратя время на сжатие при каждом запросе.
- **Шрифты.** В `soffice.data` входят не все письменности: CJK-набор
  добавляется отдельно. Способ включения (в образ файловой системы
  на сборке или подгрузкой в рантайме) ещё не проверен.
- **Один документ за раз.** Офис держит открытым не более одного документа:
  линейная память сборки — 1 ГБ, и два документа делили бы её. Поэтому
  и предпросмотр, и конвертация идут через одну очередь (`queue.ts`), а
  начатую операцию прервать нельзя — у моста нет отмены, и задача доводится
  до конца или до таймаута (300 с). Прервать можно только ожидающую.
- **Путь исходника уникален для задачи** (`paths.ts`). Офис переиспользует
  открытый документ по пути, поэтому у двух файлов пути обязаны различаться:
  иначе предпросмотр одной книги и экспорт другой работали бы с первым
  документом, а второй файл молча перезаписывался бы под ним.
- **Результат живёт в памяти вкладки.** Готовый PDF отдаётся blob-адресом
  (в отличие от серверного маршрута, где ссылка ведёт в хранилище и живёт
  час), и освобождается при уборке строки или уходе со страницы. Пользователю
  это сказано в строке задачи: «скачайте до закрытия страницы».
- **Мобильные браузеры.** Ограничение памяти вкладки делает путь
  неприменимым; это надо подтвердить замерами, а не предполагать.

## Почему офис работает в главном потоке

Соблазн вынести сборку в Web Worker понятен: большой модуль, свои воркеры,
страница не должна подвисать. Проверка показала, что **сборка этого
не поддерживает, а переносить нечего**.

**Не поддерживает.** При инициализации сборка сама передаёт canvas в поток
рендеринга: имена переданных canvas приходят из атрибутов GL-контекста,
которые задаёт Qt-бэкенд (по умолчанию `#qtcanvas`), а сам элемент она ищет
через `document` — и, не найдя, останавливается с `pthread_create: failed to
transfer control of canvas "#qtcanvas" to OffscreenCanvas!`. В воркере
`document` нет, и передать канвас «снаружи» не получается: сборка не берёт
его ни из `Module.canvas`, ни из `Module.transferredCanvasNames` — и то и
другое проверено запуском. Обойти это можно только подделкой DOM внутри
воркера, то есть обвязкой поверх вендорского кода, который править нельзя.

**Нечего переносить.** Замер в браузере (Chrome, headless) на книге 819 КБ
(три листа, 60 000 строк): предпросмотр — 2 с, конвертация — 1 с, готовый PDF
1,3 МБ. `PerformanceObserver` по `longtask` за это время **не зафиксировал
ни одной длительной задачи**: сборка считает в своих pthread-воркерах, а
главный поток остаётся свободным — он занят разве что записью исходника
в файловую систему сборки (32 МБ на предельном размере) и чтением готового
файла. Ради этого переносить всю инициализацию в воркер, теряя поддержку
вендора, было бы решением без задачи.

Остаётся вопрос о **нескольких офисах сразу** (конвертировать несколько
файлов параллельно): каждый экземпляр — это ещё ~1 ГБ линейной памяти, и
обсуждение упирается в память вкладки, а не в поток исполнения. Если
понадобится, экземпляры придётся разводить изолятами (iframe со своей копией
сборки), а не воркерами.

## Dev-режим

Правки страницы проверяются без сборки образа: `npm run dev:web` поднимает
dev-сервер на `http://localhost:5173/`. Нужны собранные пакеты (движок
собирается как библиотека, страница берёт его из `dist`) и скачанная сборка —
те же, что и для образа:

```bash
pnpm --filter @doc-converter/contract build
pnpm --filter @doc-converter/office build
node apps/web/lowa/fetch.mjs
npm run dev:web
```

Раздачу dev-сервер берёт на себя, и тем же составом, что даёт nginx:
заголовки изоляции — из `vite.config.ts`, сборка LibreOffice — из
`apps/web/lowa/assets` по `/lowa/`, мост — сборкой `vite.bridge.config.ts`
в память (`apps/web/dev/office-dev.ts`). Конфигурация моста вызывается как есть, а не
переписывается: формат (IIFE для `importScripts`), имя файла и выключенная
минификация заданы в одном месте, и вторая их копия разошлась бы с первой
молча — мост, собранный модулем, воркер офиса не загрузит, а снаружи это
выглядит как «офис не запустился за 120 секунд».

Отличия от прод-раздачи осознанные:

- **файлы идут несжатыми.** В образе рядом с распакованными лежат их
  `.gz`-копии, и nginx отдаёт именно их (`gzip_static on`): около 78 МБ вместо
  250 МБ. В dev-режиме сжатия нет — на localhost экономить нечего, а прогресс
  загрузки честнее: полоса показывает ровно то, что скачано, тогда как в проде
  `content-length` сжатого файла меньше распакованного объёма;
- **кеш — `no-cache` с `ETag`**, а не годовой `immutable`: в проде имя файла
  защищено контрольными суммами, а здесь под тем же именем после повторного
  `fetch.mjs` окажется другое содержимое. Повторная отдача стоит запроса
  с ответом 304, и при 154 МБ это заметно — страница в dev перезагружается
  часто.

Проверка dev-режима машинная там, где ошибка иначе не видна: разбор пути
файла сборки (выход за каталог), типы содержимого (с чужим типом `.wasm`
сборка молча теряет потоковую компиляцию, а `.js` при `nosniff` не грузится
вовсе), совпадение заголовков изоляции с `nginx.conf` и совпадение адресов
файлов офиса с тем, что раздаёт плагин, — в `tests/office-dev.test.js`.

## Как воспроизвести проверку

Сборку нужно получить один раз — она в репозитории не хранится:

```bash
node apps/web/lowa/fetch.mjs      # скачивает файлы, распаковывает brotli,
                                  # сжимает крупные в .gz, пишет assets.sha256
```

Дальше — тот же путь, что у пользователя, только локально:

```bash
docker compose up --build          # web раздаёт страницу и сборку
```

Адрес — `http://localhost:8080/`. Что должно произойти: файл выбирается
в общей зоне (той же, что и для серверного маршрута), кнопка «Загрузить офис»
в панели «Офис в браузере» скачивает сборку с прогрессом (около 78 МБ),
«Предпросмотр» в строке файла рисует его в canvas, «В браузере» отдаёт
готовый PDF на скачивание. Если canvas остаётся пустым, а число листов
при этом считается верно — смотрите раздел про настройки конфигурации выше.

**Раздача обязана быть с заголовками.** Их выдаёт `nginx` из `nginx.conf`
(локация документа `= /index.html`, заголовки достаются и корню: его отдаёт
SPA-fallback через внутренний редирект). Без них браузер не даёт
`SharedArrayBuffer`: сборка не стартует, а в консоли видно ошибку про
`pthread`. Заголовок принадлежит документу, поэтому любая другая раздача —
статический сервер, внешний прокси, dev-сервер Vite — обязана выдать их сама;
в dev-режиме это делает `vite.config.ts` (см. раздел «Dev-режим» выше),
а совпадение значений с `nginx.conf` проверяет `tests/office-dev.test.js`.
Разойдясь, они дали бы страницу, которая работает в одном из двух режимов
и молча отказывает в другом.

В браузере эта проверка проходит и автоматически: прогон в headless-браузере
(`page_run.mjs` из спайка, вне репозитория) открывает страницу, нажимает те же
кнопки и сверяет скачанный PDF — имя файла, размер, число страниц. Спайк
в поставку не входит и нужен ровно для этого: проверять то, что иначе
проверяется только глазами.
